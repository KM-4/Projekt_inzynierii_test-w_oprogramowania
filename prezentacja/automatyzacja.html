Mateusz Krzyzak · API i automatyzacja · ← powrót do strony głównej

Struktura projektu

05_Automation/
├─ tests/        api.spec.ts (10 testów API), ui.spec.ts (12 testów E2E)
├─ api/          warstwa API: klienci, buildery danych, endpointy, typy, fixture
├─ pages/        Page Object Model: HomePage, ContactForm, ReservationPage, AdminLoginPage
├─ helpers/      audit.ts (evidence, asercje, screeny, maskowanie), result-reporter.ts
└─ playwright.config.ts

Konfiguracja runnera

ElementUstawienie
Projektyapi – APIRequestContext, bez przeglądarki i bez trace; ui-chrome – Chrome, trace i screenshot przy FAIL
Stabilność1 worker, 0 retry, brak sztucznych oczekiwań – nie obciążamy publicznej instancji i nie maskujemy niestabilności
DaneID z bieżących list, unikalne znaczniki QA, sprzątanie wyłącznie własnych rekordów
Statusyreporter mapuje passed → PASS, failed → FAIL, skip z powodem → BLOCKED (case-results.json)
Sekretydane administratora tylko w zmiennych QA_USERNAME / QA_PASSWORD; maskowanie w evidence i raportach

Uruchomienie

npm ci --ignore-scripts --no-audit --no-fund
$env:QA_USERNAME='<login>'; $env:QA_PASSWORD='<hasło>'
npm test                  # 22 testy, ok. 30 s
npm run test:api          # tylko API
npm run test:ui           # tylko E2E
npm run report:project    # raport z testów (HTML)

Oczekiwany wynik: 14 passed, 5 failed, 3 skipped (BLOCKED). Kod wyjścia 1 oznacza wykryte defekty SUT.

Od przebiegu do dokumentów

  1. Przebieg – npm test zapisuje evidence (JSON, screeny) i raporty runnera (HTML, JSON, JUnit, case-results.json).
  2. Metryki – collect-results.mjs przelicza przypadki, metryki, defekty i macierze.
  3. Dokumenty – generatory tworzą PDF (01, 03, 06), Markdown (02, 04), raport z testów i tę prezentację.
