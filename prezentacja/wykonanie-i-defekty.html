Evidence

Dla każdego przypadku powstaje plik evidence/{api|ui}/<ID>.json z listą żądań (request, response, status) i asercji (oczekiwane, otrzymane, wynik). Testy E2E zapisują wycinki ekranu po każdym istotnym kroku. Sekrety, tokeny i ciasteczka są maskowane przed zapisem.

Raporty defektów

Severity według skali prowadzącego: S1 – blokada kluczowego procesu, S2 – istotna funkcja bez obejścia, S3 – problem z obejściem. Kilka przypadków z tym samym objawem to jeden defekt.

DEF-01 – Trasy zasobów z ID zwracają 500; rezerwacja UI i sprzątanie danych zablokowane S1 Critical · P1

ŚrodowiskoWindows 11; Chrome 157.0.8103.78; Playwright 1.62.1; Node 22.16.0; Europe/Warsaw; publiczne proxy /api/*; UI v2.2
Warunki wstępnePubliczna lista pokoi dostępna; roomid pobrany dynamicznie. Dla wiadomości/rezerwacji: utworzony własny rekord i bieżący token.
Kroki reprodukcji
  1. GET /api/room, wybierz istniejący roomid.
  2. GET /api/room/<roomid>: porównaj status.
  3. Otwórz /reservation/<roomid>?checkin=<przyszła data>&checkout=<data+2>.
  4. Dodatkowe reprodukcje tego samego symptomu: utwórz własny message lub booking, znajdź jego ID na liście, wykonaj GET, PUT i DELETE własnego ID z tokenem.
OczekiwaneGET istniejącego pokoju/rekordu 200; nieistniejący pokój 404; UI pokazuje szczegóły i rezerwację; PUT i DELETE własnego rekordu 200 w proxy.
RzeczywisteHTTP 500 i tekst Internal Server Error na dynamicznych trasach (GET, PUT, DELETE). UI pozostaje na spinnerze; poprawne POST i listy działają. Aktualizacja i sprzątanie własnych danych również kończą się 500.
Uzasadnienie severityBlokada głównego procesu rezerwacji gościa (S1 według skali prowadzącego). Brak sensownego obejścia w zwykłym UI. Pozostałości danych testowych do resetu.
DeduplikacjaJeden raport grupuje wspólny, powtarzalny symptom tras z ID w kilku usługach. Nie twierdzimy, że znamy wspólną przyczynę. Po diagnozie właściciel może rozdzielić zakres naprawy; nie liczymy każdego HTTP 500 jako nowego defektu.

DEF-02 – Email jako obiekt JSON w wiadomości powoduje HTTP 500 S3 Medium · P3

ŚrodowiskoWindows 11; Chrome 157.0.8103.78; Playwright 1.62.1; Node 22.16.0; Europe/Warsaw; publiczne proxy /api/*; UI v2.2
Warunki wstępnePubliczny POST /api/message dostępny, pozostałe pola poprawne.
Kroki reprodukcji
  1. Przygotuj poprawny payload wiadomości jak w API-06.
  2. Zastąp email obiektem {"value":"qa@example.test"}.
  3. Wyślij POST /api/message z Content-Type application/json.
  4. Sprawdź status i treść odpowiedzi.
OczekiwaneBłędny typ pola String jest błędem danych klienta i powinien być odrzucony 400; brak zapisu. Wymaganie 400 jest kryterium jakości projektu, nie cytatem specyfikacji wdrożenia.
RzeczywisteHTTP 500, JSON {"error":"Failed to create message"}. Zwykły niepoprawny format tekstowego email daje 400 w API-05. Odrzucony rekord nie pojawia się na liście wiadomości.
Uzasadnienie severityOgraniczona wada obsługi niepoprawnych danych; poprawne formularze nadal działają. Rekord nie został zapisany; brak dowodu awarii całej usługi.
DeduplikacjaOdrębny objaw POST przy złym typie, niezależny od dynamicznych tras z ID.

DEF-03 – Niepoprawny lub wycofany token odczytu rezerwacji daje HTTP 500 S3 Medium · P3

ŚrodowiskoWindows; Chrome 157.0.8103.52; Playwright APIRequestContext 1.62.1; EXP-02; publiczne /api/*
Warunki wstępneBieżący roomid pobrany z GET /api/room. Żądania odczytu, bez tworzenia rezerwacji. Do kontroli pozytywnej token z aktualnego logowania szkoleniowego.
Kroki reprodukcji
  1. GET /api/room: pobierz istniejący roomid.
  2. GET /api/booking?roomid=<roomid> bez Cookie: kontrola 401.
  3. Wyślij ten sam GET z Cookie: token=invalid-exp02-controlled.
  4. Powtórz z poprawnym tokenem z aktualnego POST /api/auth/login.
  5. Porównaj z POST /api/auth/validate dla niepoprawnego tokenu; opcjonalnie sprawdź pusty Cookie token=.
OczekiwaneNiepoprawny/nieważny token powinien dać odpowiedź autoryzacji 401 lub 403, bez danych rezerwacji. Poprawny token: 200. Sam validate dla niepoprawnego tokenu daje 403.
RzeczywisteBłędny token i pusty Cookie w GET kolekcji dają 500 oraz []; brak tokenu 401, poprawny token 200. Powtórzenie potwierdziło wynik. Wcześniej poprawny token później dostał 403 w validate i 500 w kolekcji.
Uzasadnienie severityBłąd danych/sesji jest przedstawiany jako awaria serwera. Ponowne logowanie działa jako obejście. Nie wykryto ujawnienia danych ani obejścia kontroli dostępu.
DeduplikacjaJeden raport dla niepoprawnego, pustego i później odrzuconego tokenu w tej samej operacji kolekcji. Odrębny od DEF-01: URL nie zawiera ID zasobu w ścieżce.

DEF-04 – W UTC+14 dostępność jest wyszukiwana dla dat o dzień wcześniejszych niż wybór S2 High · P2

ŚrodowiskoWindows; Chrome 157.0.8103.52; Pacific/Kiritimati (UTC+14); rzeczywisty zegar, bez mocków; kontrola UTC i Europe/Warsaw; EXP-02
Warunki wstępneKontekst Chrome timezoneId=Pacific/Kiritimati; bieżąca lokalna data ma być dzień późniejsza od UTC (badano ok. 06:48 czasu lokalnego, 16:48 UTC poprzedniego dnia). Identyczna wersja Chrome/format dat w kontekście kontrolnym UTC.
Kroki reprodukcji
  1. Otwórz stronę w kontekście Pacific/Kiritimati przy podanym warunku czasu. Zweryfikuj strefę przez Intl.DateTimeFormat().resolvedOptions().timeZone.
  2. Wpisz Check In=12/01/2027, Check Out=14/01/2027, zatwierdź Tab.
  3. Kliknij Check Availability i odczytaj request GET /api/room?checkin=...&checkout=... oraz linki Book now.
  4. Powtórz wyborem 18 i 20 stycznia 2027 z kalendarza.
  5. Kontrola: te same 12–14 stycznia w UTC. Jeżeli warunek różnicy dat UTC/lokalnej nie jest spełniony, odtwórz w odpowiednim oknie czasu; nie oczekuj tej samej reprodukcji o każdej godzinie.
OczekiwaneDaty wyszukiwania i linków odpowiadają datom widocznym w polach, niezależnie od strefy klienta: 12–14 stycznia -> 2027-01-12/2027-01-14.
RzeczywisteW UTC+14 pola/linki: 12–14 stycznia; request: 11–13 stycznia. Kalendarz: pola/linki 18–20, request 17–19. Domyślne daty też przesunięte. W kontroli UTC te same wpisane 12–14 przechodzą poprawnie.
Uzasadnienie severityWynik dostępności dotyczy innego okresu niż wybór i link rezerwacji. Może powodować błędną ofertę dostępności. Końcowy zapis i cena nie zostały sprawdzone z powodu DEF-01; nie twierdzimy, że utworzono błędny pobyt.
DeduplikacjaJeden problem konwersji dat dla trzech wariantów wejścia. UI-12 zachowuje historyczny PASS w Europe/Warsaw; nowy defekt dotyczy rozszerzenia środowiska podczas eksploracji.
